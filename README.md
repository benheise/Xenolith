# Xenolith

**An open census of which commercial products embed which third-party components.**

🔎 **Search it:** https://benheise.github.io/Xenolith/ &nbsp;·&nbsp; 🤝 **Contribute:** [three ways, below](#contribute) &nbsp;·&nbsp; 📄 **Formats:** [CONTRIBUTING.md](CONTRIBUTING.md)

## What this repository is for

When a vulnerability lands in a widely embedded component (Log4Shell in 2021, PHP2Shell and the Brotli decoder bug in October 2026), every security team asks the same question: **which of the products we run ship that component inside?** Asset scanners can't see into appliances, firmware or SaaS, and vendor SBOMs are rarely public. Each time, the community rebuilds the same vendor × product × status table by hand in a GitHub repository, then archives it when the incident ends.

Xenolith keeps that table permanently, indexed by component, so the next incident starts from what is already known. Every entry is a **sourced statement**: one claim, from one source, with a link and a date.

- **Covers:** commercial and closed-source *products*: appliances, firmware, enterprise and hosted software, management consoles.
- **Doesn't cover:** open source *packages* (libraries, frameworks, distro packages, base images). Use [deps.dev](https://deps.dev/), [ecosyste.ms](https://ecosyste.ms/), [OSV.dev](https://osv.dev/), the [GitHub Advisory Database](https://github.com/advisories) or [Repology](https://repology.org/) for those.

In geology, a xenolith is a fragment of foreign rock sealed inside a host rock: the copy of PHP inside a firewall's management console, the Brotli decoder bundled into an IDE, the Log4j jar buried in an appliance.

## Contribute

Everything is contributed by pull request and checked automatically. Pick whichever matches what you have:

| You have | Add it to | Format | Effort |
|---|---|---|---|
| A link to a vendor's **open source notices**, OSS listing, attributions document or published SBOM | [`catalog/notices.yaml`](catalog/notices.yaml) | 4 YAML lines: supplier, product, version, url | 2 minutes |
| A **vendor statement** (advisory, KB article, support reply posted publicly) that a product does or doesn't contain a component | [`community/assertions.csv`](community/assertions.csv) | One CSV row per product and component, with a source link and date | 5 minutes |
| An **SBOM** of a product: one the vendor published, or one you generated by scanning software you're allowed to analyze and share | [`community/sboms/`](community/sboms/) | CycloneDX JSON with five required `xenolith:` properties | 15 minutes |

The exact field lists, examples and the commands to check your change locally are in **[CONTRIBUTING.md](CONTRIBUTING.md)**. Pull requests run `python -m xenolith community --check`, which names the file, line and field of any problem.

**Don't submit** anything confidential, anything you aren't permitted to share, or statements you can't link to. If you work for a vendor, the best contribution of all is publishing your product's SBOM or notices at a stable public URL and adding that URL.

**Generating an SBOM for a product nobody has documented?** Scan it with Syft, cve-bin-tool or blint, then run `python -m xenolith prepare scan.cdx.json --supplier … --product … --version … --artifact <file> --attest`. It adds the required fields, hashes the artifact, strips local paths and validates the result ([how](CONTRIBUTING.md#3-submit-an-sbom)). [design/xenolith-scan.md](design/xenolith-scan.md) is the plan for a single cross-platform scanner that does the whole job in one step.

## How it works

```
catalog/components.yaml       watchlist: components, the CVEs that identify them, affected version ranges
        │
        ├─ Vendor CSAF/VEX feeds ──────────┐  "Product P is fixed / known_affected / not affected
        ├─ Vendor open source notices ─────┤   by CVE-X", or "P lists component C 1.0.6"
        ├─ NCSC-NL and CISA trackers ──────┤
        ├─ community/ (statements, SBOMs) ─┤
        │                                  ▼
        │                     data/assertions/**/*.ndjson   (open data, one sourced claim per line)
        │                                  │
CVE records + CISA KEV ──► data/spine/products.ndjson       (product registry with CPEs, ranked by KEV and CVE counts)
                                           │
                    identity aliases + CPE links merge each product onto one page
                                           ▼
                             docs/  (static search site on GitHub Pages, rebuilt daily)
```

1. **Component watchlist.** [`catalog/components.yaml`](catalog/components.yaml) lists widely embedded components, the CVEs that identify them, the names they appear under in notices, and the affected version ranges from each CVE record.
2. **Vendor advisories (automated).** A crawler reads CSAF 2.x feeds from Cisco, Microsoft, Red Hat, Siemens, Schneider Electric, ABB, SICK, CISA and every provider on BSI's CSAF aggregator. A vendor's status for a watchlist CVE is a statement about whether the product embeds the component. The crawl is incremental.
3. **Vendor open source notices (automated).** "Open Source Used In" documents, OSS listings and third-party notices are the closest public stand-in for an SBOM of a closed product. `python -m xenolith notices` fetches the documents in [`catalog/notices.yaml`](catalog/notices.yaml) (PDF, HTML, text, CycloneDX, SPDX), keeps the **full** component list and matches it against the watchlist. Sources so far: Palo Alto Networks (every OSS listing, discovered automatically), Elastic (per-release dependency reports), Ivanti Connect Secure and Secure Access Client, WatchGuard Fireware, Tenable, F5 BIG-IP and Citrix NetScaler. Vendors checked and found not crawlable are listed at the bottom of that file.
4. **Incident trackers (seed data).** NCSC-NL php2shell and log4shell, and CISA's log4j-affected-db, imported with full provenance.
5. **Community submissions.** Statements and SBOMs contributed by pull request (see [Contribute](#contribute)).
6. **Product registry.** Vendor/product names from CNA-published CVE records and the CISA KEV catalog, ranked by exploitation, with the CPE identifiers the CNA or CISA's ADP container gives them. Products with no composition data yet are listed too, which makes the gaps visible.
7. **Vulnerable-version check.** When a notices file or SBOM lists a component version inside a CVE's affected range, the statement is flagged "Vulnerable version listed". Vendors often backport fixes without changing the version string, so this is a reason to ask the vendor, not proof of exposure.
8. **One page per product.** Supplier and product names are canonicalized ([`catalog/identity.yaml`](catalog/identity.yaml): legal suffixes, repeated vendor names, aliases like Pulse Connect Secure → Connect Secure). Entries that share a CPE vendor:product (from CVE records or vendor CSAF product trees) are then linked automatically, with guards against generic CPEs, mismatched names and different release numbers. Every link is listed in `docs/data/crosswalk.json`.
9. **Static site.** `python -m xenolith build` writes JSON for the single-page search UI in `docs/`. A daily GitHub Actions run refreshes everything and republishes.

### Reading a statement

| Status | Meaning |
|---|---|
| Affected | Product contains a vulnerable version; no fix stated |
| Workaround only | Affected; vendor published a mitigation but no fix |
| Fix released | Product contained the component; vendor has shipped a fixed version |
| Investigating | Vendor or tracker hasn't concluded |
| Uses host runtime | Product runs on a copy you install and patch yourself (e.g. a PHP app) |
| Contains (not assessed) | Component is listed in the vendor's notices, an SBOM or a scan; no CVE assessed |
| Vulnerable version listed | The listed component version falls inside the CVE record's affected range. Confirm with the vendor |
| Not affected | Vendor says the product isn't affected |
| Not present | Vendor says the component isn't in the product at all |

Tracker rows are only as current as the tracker (the Log4j trackers were archived in 2022–2023). Always confirm against the vendor's own advisory before acting.

## Running it locally

Requires Python 3.11+, PyYAML and pypdf.

```bash
pip install -r requirements.txt

python -m xenolith community --check                   # validate community/ (what pull requests run)
python -m xenolith notices --only "Example Networks"   # fetch and parse notices documents (incremental)
python -m xenolith csaf --only Cisco --max-fetch 200   # vendor CSAF feeds (incremental)
python -m xenolith spine                               # KEV-only registry; add --cves <cvelistV5/cves> for the full one
python -m xenolith build                               # write docs/data/

python -m http.server -d docs 8000                     # open http://localhost:8000
python -m unittest discover -s tests
```

Incident trackers are ingested from local clones: `git clone --depth 1 https://github.com/NCSC-NL/php2shell src/NCSC-NL_php2shell` (likewise `NCSC-NL/log4shell` and `cisagov/log4j-affected-db`), then `python -m xenolith trackers --src src`.

## Repository layout

| Path | What |
|---|---|
| `catalog/` | Component watchlist with affected ranges, data source registry, CSAF provider list, notices document list, identity aliases |
| `community/` | Contributions: `assertions.csv`, `sboms/` and `examples/` |
| `data/assertions/` | Normalized statements per source (NDJSON). The open data dump |
| `data/notices/`, `data/community_sboms/` | Full component inventories, one JSON file per document or SBOM |
| `data/spine/products.ndjson` | Product registry |
| `data/state/` | Crawl state so documents are only re-fetched when they change |
| `design/` | Design notes, including the recommended scanning tool |
| `docs/` | The GitHub Pages site (`index.html` + generated `data/`) |
| `schema/assertion.schema.json` | JSON Schema for one statement |
| `xenolith/` | Pipeline code (standard library + PyYAML + pypdf) |

## Roadmap

- [x] Seed from NCSC-NL and CISA incident trackers
- [x] Incremental CSAF/VEX crawler with aggregator discovery
- [x] Product registry from CVE records + KEV
- [x] Static search site and daily refresh
- [x] Parse vendor third-party notices into full component lists
- [x] Flag listed component versions that fall in a CVE's affected range
- [x] Product identity: name canonicalization, alias table and automatic CPE linking
- [x] CycloneDX 1.6 export of any product's inventory; CycloneDX SBOM submissions
- [x] `xenolith prepare`: turns any scanner's CycloneDX or SPDX output into a validated, path-stripped submission
- [ ] `xenolith-scan`: one cross-platform, offline binary that unpacks an installer, firmware image or container and produces a submission ([design](design/xenolith-scan.md))
- [ ] `catalog/fingerprints.yaml`: symbol and version-string fingerprints for watchlist components, shared with the scanner
- [ ] Transparency Exchange API (TEA) client to collect vendor SBOMs as vendors publish them
- [ ] More notices sources (Oracle licensing manuals, Splunk credits and JetBrains need custom handling)
- [ ] Bulk CycloneDX/SPDX export of all inventories for GUAC or Dependency-Track
